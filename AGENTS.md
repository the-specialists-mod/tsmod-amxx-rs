# AGENTS.md

Guidance for coding agents (and people) working in this repository: AMX Mod X's TS modules,
**tsx** and **tsfun**, and **hamsandwich**, ported to Rust for the Rust port of The Specialists 3.0
([the-specialistsmod-rs](https://github.com/the-specialists-mod/the-specialistsmod-rs), checked
out at `../rust-hlmod-the-specialists`).

Start with [README.md](README.md), then [docs/design.md](docs/design.md).

## Sources of truth

| Question | Where to look |
|---|---|

| What stock hamsandwich does | `../ref/amxmodx/modules/hamsandwich` (`hook_native.cpp` table and registration, `hook_callbacks.cpp` call protocol, `call_funcs.cpp` ExecuteHam, `DataHandler.{h,cpp}`, `pdata.cpp`), `plugins/include/hamsandwich.inc`, `ham_const.inc` |
| The entity hook contract | The port's `crates/plugin-api/src/lib.rs` ("Entity hooks") and `docs/implementation/plugin-api.md` §7 (which functions fire for which classes; the dev aid `ts_dev_hamlog 1`, never left on in e2e) |
| The module and metamod ABIs | `../ref/amxmodx/public/sdk/amxxmodule.{h,cpp}`, `amxmodx/amx.h`, `amxmodx/CModule.cpp`; `../ref/metamod/metamod/{meta_api,plinfo,mutil}.h` |
| What the server sends and how TS behaves | The port: `crates/shared/src/protocol` (message layouts), `crates/plugin-api` (the plugin API contract), `docs/implementation/plugin-api.md`; the TS decomp at `../ts30-decomp` |
| How plugins use the modules | `../ref/ts-plugins` (real plugins; data only, never run their scripts) |

Port behaviour from upstream's source, not from memory. When this port deliberately differs,
add it to `docs/design.md` §6 and the README's native table.

## Layout and the `unsafe` boundary

```
crates/amxx/    AMX Mod X module SDK + metamod glue: all the FFI (unsafe allowed)
crates/tsx/     the TSX module; #![deny(unsafe_code)] except src/ffi/
crates/tsfun/   the TSFun wrapper (module info only)
crates/hamsandwich/  Ham Sandwich; #![deny(unsafe_code)] except src/ffi/. src/hooklist.rs is
                generated by gen_hooklist.py from upstream (python3 -I gen_hooklist.py
                <hook_native.cpp> <ham_const.inc> src/hooklist.rs); don't edit it by hand
xtask/          cargo xtask build | dist | lint | test | e2e
e2e/            tsx_e2e.sma and ham_e2e.sma, the end-to-end test plugins
include/        tsxaddon.inc (ts_setuserammo is a tsx native), tsconst.inc (TS 3.0's weapon
                ids) and tsfun.inc (the forwards tsx fires, ts_set_fuattack), patched
```

1. **`unsafe` lives in `crates/amxx` and the modules' `src/ffi/` only.** Every `unsafe` block has a
   `// SAFETY:` comment saying why it holds (`clippy::undocumented_unsafe_blocks` is on; `cargo
   xtask lint` makes it an error). Never weaken `deny(unsafe_code)` in tsx or hamsandwich.
2. **New engine or AMX Mod X access goes into `amxx` as a safe wrapper**, then tsx calls it
   through the `game::Game` trait, which `ffi::game::RealGame` implements (and
   `testing::FakeGame` fakes); hamsandwich likewise through `host::Host`/`host::HamApi`
   (`ffi::host::RealHost`, `testing::FakeHost`). Keep hooks in `ffi/hooks.rs` thin: convert pointers to indices
   and strings, call a `State` method, fire forwards.
3. **Don't hold the state across a call that can reach a plugin** (forwards, `MDLL_Use`/`Touch`,
   API setters, which may send messages). `state::with` returns `None` instead of panicking on
   re-entry, which would silently drop data: release, call out, take it again.
4. **Exports**: `amxx::export_module!` (`AMXX_*`) in every module, `amxx::export_metamod!`
   (`Meta_*`, `GiveFnptrsToDll`) in tsx and hamsandwich (for the engine table and the API
   lookup) only. AMX Mod X treats any library exporting `Meta_Attach` as a metamod plugin.

## Build and test

Requirements: Rust stable with `i686-unknown-linux-gnu` and `i686-pc-windows-gnu`, clang ≥ 18,
32-bit glibc/libgcc, MinGW-w64, and `../xash3d-fwgs` (with `3rdparty/library_suffix`) or
`FWGS_DIR`: `goldsrc-sys` (a git dependency on the port) generates its bindings from the FWGS
headers. `.cargo/config.toml` sets `FWGS_DIR` to `../xash3d-fwgs` unless the environment has it;
xtask instead looks for `xash3d-fwgs` next to the checkout or any ancestor, so `cargo xtask` also
works from a worktree under `.claude/worktrees/` (plain `cargo` there needs `FWGS_DIR`).

```sh
cargo xtask test                 # unit tests, host and i686 (i686 runs the ABI layout tests)
cargo xtask build [--release]    # both targets; must build without warnings
cargo xtask lint                 # cargo fmt --check, clippy --all-targets -D warnings, both targets
cargo xtask dist [--debug-info]  # dist/<platform>/addons/amxmodx/modules/ with AMXX's file names
                                 # (+ scripting/include/tsxaddon.inc, tsconst.inc, tsfun.inc); checks the DLLs import no
                                 # MinGW runtime and the metamod modules export GiveFnptrsToDll
cargo xtask e2e [linux] [win]    # end-to-end, below (~1.5 min per root)
```

`e2e` needs the AMX Mod X test roots from `../ref/amxx-testenv` (its README): `setup.sh`
builds `~/games/amxx_rehlds_linux` / `amxx_rehlds_win` (ReHLDS + Metamod-R + AMX Mod X 1.10)
from the port's `dist/`, so rerun it after a new port build (`cargo xtask --release dist` there).
xtask installs the release modules (hamsandwich under the stock module's file name) and
`e2e/*.sma` (compiled with that env's `amxxpc`, with `include/` first) into the root, starts a
4-bot server on `ts_dojo` with the env's `run.sh`, waits for each plugin's `DONE` line in
`ts/addons/amxmodx/logs/<plugin>.log`, then runs the stats round trip: upstream's
`tsstats.sma` is the score plugin (`data/tsstats.amxx`), a `changelevel` saves `tsstats.dat`
(`ServerDeactivate`), which must equal the rank `tsx_e2e` dumps on the next map; `quit`, and a
bot-less restart with `e2e/tsstats_score_e2e.sma` as the score plugin must load the same entries
in its reversed order. It fails on any `CHECK ... FAIL`, a stats mismatch, a module missing from
`amxx modules`, or a `[TSX]`/`[HAMSANDWICH]` line in the AMX Mod X error log other than the
intended ones (the unknown-class error and ham_e2e's `ExecuteHamB(Ham_Use)` refused at the
server's 8-deep nesting limit). `ham_e2e` skips its checks when the server lacks the entity
hooks. It refuses to start while a server runs in that root. Overrides: `AMXX_TESTENV`,
`AMXX_SCRIPTING`, `AMXX_TSSTATS_SMA`, `AMXX_LINUX_ROOT`, `AMXX_WIN_ROOT`, `E2E_TIMEOUT`;
`E2E_NO_STATS=1` skips the round trip (stops with `stop.sh`).

Before calling a change done: `cargo fmt`, `cargo xtask test`, `cargo xtask lint`, and
`cargo xtask e2e linux win` for anything that touches hooks, natives or exports. When exports
change, compare `nm -D --defined-only` / `objdump -p`.

## Conventions

- **Keep upstream's interface.** Native names, argument order, return values and errors,
  forwards, library/class names (`tsx`/`xstats`, `tsfun`, `hamsandwich`), cvars, localinfo keys and the
  `tsstats.dat` format are what compiled plugins and existing servers depend on.
- **Cite upstream.** Doc comments name the upstream function a piece ports (``/// `CPlayer::saveKill` ``),
  and file headers credit the AMX Mod X Development Team (GPL-3.0-or-later with the AMX Mod X
  exceptions).
- **Formatting** is rustfmt's (`rustfmt.toml`: 140 columns, `use_small_heuristics = "Max"`).
- **Comments say why**, not what. Doc comments on public items.
- **Docs move with the code**: README's native table, `docs/design.md` (behaviour, deviations,
  test results) in the same change.
- **Port additions are marked** in comments (e.g. the `TSPAward` cache, shot counting from
  events).

## Pitfalls

- **The bindings' `enginefuncs_t` is FWGS's**, longer than metamod's: never copy whole engine
  tables, write fields (`amxx::meta` does).
- **The server sends bots no `WeaponInfo`/`WStatus`/HUD updates of their weapon**: their weapon
  in hand comes from the API or `pev->weaponmodel`.
- **The API's `player_info` is a per-frame snapshot**: a getter right after a setter sees the old
  value. Tests that check a setter's effect wait a frame (`e2e/tsx_e2e.sma` uses 0.3 s).
- **TS 3.0 never sends `ClipInfo`**, upstream's shot source; shots come from fire events.
- **Bot AI switches weapons by itself**: the e2e weapon check re-issues `weapon_13` and looks
  again.
- **amxxpc** needs its own directory on `LD_LIBRARY_PATH`. `state` is a Pawn keyword. 1.8.2's
  amxxpc exits 0 after compile errors (xtask deletes the output first), and its `.amxx` is the
  only kind 1.8.2 loads; `AMXX_VERSION_NUM` is 182 / 190 / 1100.
- **Entry from AMX Mod X runs on a realigned stack** (`amxx::stack::aligned`, in `natives!`'s
  dispatch and the `AMXX_*` exports): 1.8.2's Linux core calls in with `esp` = 8 mod 16 and Rust's
  i686 Linux code faults on its SSE spills (#17). `-C llvm-args=-stackrealign` does nothing in
  rustc. A new kind of entry point from the core needs the same.
- **How a server stops decides whether `tsstats.dat` is saved**: `changelevel` and `quit` run
  `ServerDeactivate` (on both roots); `stop.sh`'s SIGTERM does on Linux (ReHLDS shuts down) but
  not under Wine. xtask installs no rank file, so "Could not load stats file" on the match's start
  is expected.
- **Stopping servers**: use the testenv's `stop.sh` (name + cwd match), never `pkill -f`.
- **`ExecuteForward` reads `FP_FLOAT` varargs as doubles.** hamsandwich registers float
  parameters as `FP_CELL` and passes the float's bits, so every vararg is cell-sized.
- **hamsandwich's frames are a stack**: the server calls the hook before and after the function,
  possibly with nested calls in between (forwards dealing damage, `ExecuteHamB`), and calls post
  exactly when it called pre. Post matches the top frame by `(ham, this)`; never by the
  `HamCall` address, which changes between pre and post (the server moves the struct). Stock decides the return by the *last* forward's result, not the
  highest; keep that.
- **The plugin API is versioned, not append-only**: `amxx::tsapi::find` takes only the exact
  version this build's `ts-plugin-api` has (6, `TSRS_PluginApi006`). A port API bump means
  repinning the port crates and moving the modules in the same round.

## Git

- Work on `main`. Commit in logical steps; commit or push only when asked.
- Releases: push a `v*` tag; `.github/workflows/release.yml` builds both platforms, checks the
  Windows imports and publishes `tsmod-amxx-rs-<tag>-<platform>.zip`. It pins the FWGS commit
  the port's release workflow uses; bump both together.
- The port crates (`goldsrc-sys`, `ts-plugin-api`, `shared`) are git dependencies pinned to one
  rev in the root `Cargo.toml`.
